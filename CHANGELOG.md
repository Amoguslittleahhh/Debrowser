# Changelog

## 1.5.0

The things a browser is expected to have. Right-clicking a page did nothing at all; `Ctrl+L` could not reach the address bar; there was no find in page; the start page was a wordmark and a box; Settings was eight sections in one scroll with no way to see what they were. None of that was a decision — it was a list of things not written yet, and it is written now.

And it stops looking generated. The palette was a blue-black under a saturated cornflower blue, which is the default of every dark interface made in the last two years and nameable from a thumbnail. It is a warm neutral ink now, with one petrol-teal accent and a light theme that is paper rather than white — and, it turned out, with the checkboxes finally in the browser's own colour instead of Chromium's.

Two of the entries below are defects found by measuring rather than by reading, which is the only reason they were found at all: `findInPage` refusing to report a match count when it is passed the option the documentation recommends, and a saved colour that would have outlived the palette that produced it.

The suite has grown from 105 checks to 125.

- **One keyboard table instead of two that disagreed.** The chrome bound `Ctrl+L`, `Ctrl+D` and `Ctrl+Shift+B` in its own page; the browser process bound a different set to each page's renderer. So which shortcuts existed depended on which view happened to hold focus — and a page holds it nearly all the time, which is why the address bar could not be reached from the keyboard at all and why Settings advertised `Ctrl+Shift+B` for a binding that only ever ran while the toolbar was focused. There is one table now, every view answers it exactly once, and the app menu prints its accelerators from the same rows, so a label and the key it names cannot drift apart. New along the way: reopen closed tab, switch tabs by number and by `Ctrl+Tab`, back and forward on `Alt`+arrows, zoom keys, view source, and find.
- **Right-clicking a page does something.** There was no context menu at all — Electron fires the event and, unless something answers it, no menu appears. It is drawn in the same view as the app menu and loads the same stylesheet, so the two cannot drift apart, and what is in it comes from Chromium's own hit test: a link, an image, an editable field or a selection, then the page itself. The address an item carries is the one that was actually under the pointer, and it is refused unless it is `http`, `https` or one of the browser's own pages — a menu that will open whatever a renderer names is a page opening tabs on your behalf.
- **Find in page, on `Ctrl+F`.** A strip of chrome that takes its own 38px from the content, the way the bookmarks bar does, rather than a card floating over the top-right corner of the page — which is where Chrome puts it and where, on a page of search results, it covers the first result.
- **Writing that turned up a defect in Electron itself, measured rather than assumed.** `findInPage(text, { findNext: false })` — which the documentation describes as beginning a new search, and which is the obvious way to write a search-as-you-type — fires no `found-in-page` event at all, while the same call with the options left off fires it normally. That event is the only source of a match count, so the count would have stayed empty on every keystroke. Bisected against the real thing: `{ forward: true }`, `{ findNext: true }` and `{ matchCase: false }` all report; `{ findNext: false }` alone is silent.
- **The new tab page has the sites you actually go to on it.** It was a wordmark and a search box. It still makes no request of its own — the tiles come from the browser's own history, folded by origin, and a site's logo is fetched by the browser process without cookies, because an `<img>` pointed at the site would tell eight companies every time you open a tab. But a start page with nothing on it is not restraint, it is a page that makes you type an address you visit every day. Removing a tile forgets the site, because a tile that came back tomorrow would be a button that does nothing.
- **Settings has a rail and a search box.** Eight sections in one scroll, with no way to see what they were without scrolling through them. The rail is built from the sections themselves rather than being a second list to keep in step, it marks where you are as you scroll, and the search filters the rows that are already on the page — so there is still exactly one list of settings in the codebase.
- **A palette of its own.** The old one was `#16181d` surfaces under a `#5b8cff` accent: a blue-black with a saturated cornflower blue on it, which is the default of every dark interface generated in the last two years and nameable from a thumbnail. The base is a warm neutral now — red and green sit two or three points above blue in every surface, so it reads as ink rather than as screen — and the one accent is a petrol teal, cool on a warm ground and far enough from the three alert colours that nothing here can be confused for anything else. The light theme is paper on the same terms: warm off-white on a warmer ground rather than white on blue-grey. Radii are tighter, the focus ring is crisper, and the accent swatches are six mixed pigments rather than six primaries.
- **The controls Chromium draws now follow that accent too.** `color-scheme` tells the engine which way round the interface is and nothing about colour, so every checkbox, radio, slider and progress bar was painted in Chromium's own blue. Photographed on Settings: a column of bright blue checkboxes in a browser with no blue anywhere else in it. One declaration fixes all of them, and it is the same class of bug as the `color-scheme` one before it — the part of the palette a stylesheet cannot reach by styling the element, because the element is not ours to style.
- **The site chip is one component instead of six.** Two stylesheets held byte-identical copies of it and four more held near-identical ones, which is the drift the shared stylesheet exists to prevent and had already cost one real bug — the chip painting behind transparent favicons, so every logo in the browser sat on a coloured tile with the site's initial showing through it.
- **Tabs grow to fill the strip.** They stopped at 200px, so five tabs left a few hundred pixels of empty strip after the `+`. Chrome's tabs expand to 240 and so do these.
- **The downloads button fell into the same hole the star fell into.** No explicit `order` in the sidebar means 0, which sorts before 1 — so the leftmost control in the browser was a download arrow that is hidden most of the time.
- **The task manager's first figure had a label that had to be hovered to be read.** `RESIDENT (OVE…`, truncated in its own tile. One word now, and amber where the platform's figure is known to run high.
- **And a cleanup pass, which is why some of this is shorter than it was.** Eleven copies of three URL helpers became three; the site mark, built by hand in four views, became one component; the context menu stopped being a copy of the app menu and now shares its glyphs, keyboard and dismissal with it; and three separate paths were theming a view, none of them before its first paint — the browser hands the whole palette to a view as it builds it now, so nothing flashes. No behaviour was meant to change, and the photographs of all ten views are identical either side of it.
- **A second review pass, over the whole branch, found seven more.** `Ctrl+F` opened the find bar but left the keyboard in the page, so every letter typed went to the page rather than to the field — the same mistake `Ctrl+L` had already been fixed for. The find bar was only accounted for in the horizontal layout, so with the tab strip down the side it was drawn inside a column that is ten pixels wide until the pointer arrives: opened from the keyboard it was laid out off the side of the window, where nobody could see it or type into it. Unpinning the side strip collapsed it to that ten-pixel edge under the pointer that had just pressed the button, because the test was on the state being entered rather than the one being left. A new tab tile pointed at whichever page of a site history happened to list last rather than at the one you actually go to, because the comparison it won was against `undefined`. A hand-edited `preferences.json` with a non-string accent threw out of the `Prefs` constructor — before there is a window — so the browser would not have started at all, which is the one outcome that file is written to avoid. The update prompt, which is the one panel that appears without being asked for, opened with **Restart now** focused, so a stray Enter aimed at the page quit the browser into an installer; it lands on **Later** now. And right-clicking away from an open context menu dismissed it but could not raise the next one, because the reopen guard meant for a toolbar button was eating a click that no button had made.
- **A colour you are already using does not become one the browser no longer offers.** Preferences are written whole, so any profile that has ever changed a setting carries the old accent and strip colours on disk — and they are still valid hex, so they load cleanly and the browser would have come up in the new surfaces under the previous cornflower blue, with nothing in Settings showing as chosen. The retired values are mapped to their replacements: someone who picked Plum wanted a purple strip, and the honest answer is the purple that exists now rather than the default.
- **Smaller things, all photographed rather than guessed.** The `+` in the side strip was a lone glyph centred in a 240px column and is a labelled row; history's visit count sat 400px from the title it counts and now sits beside it; the downloads *page* could only clear a row, with no way to open the file you had just searched for; new tab tiles overflowed their own measure; and the menu came up in the machine's colours for a frame before turning into the browser's, because a sheet took its palette from a reply rather than from the view it was created with. A review pass over all of it caught four more: the Settings filter being wiped twice a second by the governor's own state broadcast, the dropdown arrow keeping its old colour because it is a data URI and cannot see a CSS token, and the window's caption buttons being told a near-black to sit on while the light theme painted the strip white.
- **The browser's own pages are governed like any other tab.** They were pinned at ACTIVE, on the reasoning that every tier below it is wrong for them. In a real session that made three of six live renderers Settings, the downloads page and a new tab page — about 95 MB held permanently — while the actual websites beside them sat discarded at zero. A browser whose own pages are the expensive ones has the rule backwards.
- **What that exemption was really protecting was unsubmitted text,** and that is what `hasDirtyInput` is for. These pages carry the command bridge rather than the probe preload, so nothing was watching them — they report it themselves now, from the only fields that can lose anything: a search box, and the new tab page's query. Settings needs no such rule, because every control on it saves the moment it changes; there is nothing there to lose.
- **They are cheap to come back to, which is the other half of why this is safe.** A local page, landing in the renderer the prewarmer keeps warm — 46ms measured against 79ms cold — behind the same thumbnail the restore placeholder already shows.
- **The memory meter has never painted a single pixel of fill.** The bar in the toolbar is `width: 0` in the stylesheet and animated with `scaleX` in the renderer — and zero times any factor is zero. What shipped was an empty grey pill beside a figure, which reads as a broken control rather than as a gauge at 20%.
- **The address bar was invisible with the tab strip down the side.** It is styled as a recess — darker than the toolbar it sits in — which works across the top, where the toolbar is lighter. Down the side the toolbar is transparent over the strip, which is the same colour, so the most important control in the browser rendered as a line of text with a padlock next to it.
- **Tabs have a hairline between them, as they do in Chrome.** Tabs are equal width, so a short title leaves empty space inside its own tab; with no surface and no separator, five tabs read as five captions floating at intervals. The line is suppressed next to the active tab and on hover, where a separator beside a raised surface is just a seam.
- **The new tab page shows its name rather than its address.** Navigating to it left `debrowser://newtab/` in the strip and in the task manager, because clearing the title on navigation used the raw URL — right for a website, wrong for a page the browser serves itself.
- **The empty bookmarks bar is empty.** It carried "Bookmarks you save appear here", which is a sentence repeated under the toolbar of every page you visit until you save one.
- **`hidden` now means hidden, and three things were quietly ignoring it.** The engine's own `[hidden] { display: none }` is a user-agent rule, so any stylesheet declaration beats it however weak — and this interface sets `display` on nearly everything. So the toolbar's downloads button stayed visible with nothing downloaded, and in the downloads flyout every finished row kept a full progress bar and offered **Open file**, including one that had failed. One rule in the shared stylesheet fixes all of them and the next one nobody has written yet.
- **Every control the engine draws now matches the theme.** `color-scheme` was never declared, so checkboxes, scrollbars, select dropdowns, the text caret and autofill were all rendered light on a dark interface — the unchecked box on Settings' own "Reduce motion" row was a stark white square beside checked boxes that looked fine. Our stylesheets could not reach any of them: a checkbox is painted by Chromium, not by us.
- **Settings is no longer a ribbon down the middle of the window.** The column was 620px wide, so at 1280px there was more empty window either side of it than there was page — the layout of a phone screen opened on a desktop. Hints keep their own reading measure, so the explanations did not get longer with it.
- **The side strip slides out of the way, the way Zen's does.** With the tab bar down the left it is now a ten-pixel edge until the pointer reaches it, and the page keeps the whole window. Reaching the edge slides it out *over* the page rather than pushing it, so nothing reflows because the pointer brushed the window's side; moving away slides it back, after a short wait so crossing it on the way somewhere else does not close it mid-movement. A pin at the foot of the strip holds it open, and pinned it takes its column back and the page gives up the width.
- **Why it is a ten-pixel edge and not nothing.** A view is the only thing that can be told the pointer arrived, so there has to be something there to arrive at. It also bounds the idea: a view swallows every click inside its bounds, so a full-width invisible strip waiting to be hovered would make the leftmost 240px of every page unclickable.
- **And the page sits in a card rather than fused to the strip.** Edge to edge the two read as one surface — most obviously on the browser's own pages, which carry the same dark background as the strip. It is inset by a few pixels over the window's own colour now, with rounded corners. `setBorderRadius` was measured before anything was built on it: with a red window behind a white view, the pixel three in from the corner reads red and the centre reads white, so the corner really is clipped rather than the call merely being accepted.
- **The update prompt is the browser's own.** It was `dialog.showMessageBox` — a Win32 message box in the middle of a window that draws everything else itself: light-themed over a dark browser, in the system's typeface, with the system's buttons. It is a panel now, in the same sheet the app menu and the downloads flyout use, centred rather than anchored and dimming what is behind it. The one thing a platform dialog was buying here was modality, and a view over the whole window with a backdrop that catches the click was already that.
- **The browser no longer checks for updates on a schedule.** It used to re-check every six hours for the life of a window, which is it reaching out to GitHub on a schedule nobody asked for. It checks when it starts, when you open the Updates section in Settings — scrolling to a section headed "Updates" to read whether you have one is the same request as pressing the button — and when you press **Check now**. The first two share a ten-minute floor so scrolling past twice is one request; the button is never subject to it.
- **A tab that had been anywhere reported no memory at all.** The process a tab's page lives in was recorded once, when the tab was first realised, and never again — but a cross-site navigation moves the page into a *different* renderer, which is the whole point of site isolation. So every tab that had navigated once was attributed to a process it no longer used and read 0 MB, including the one in front of you; only the browser's own pages looked right, because they never leave the process they started in. It is asked of the renderer now rather than remembered.
- **Keyboard shortcuts did nothing while the task manager or a panel had focus.** They are bound to each page's renderer, which covers every tab — and covered none of the browser's own views, because the task manager has no key handling at all and the sheets handle only Escape. The task manager is a window people leave open, so this was most of the keyboard not working most of the time. Those views run the same table now; the chrome deliberately does not, because it already runs it in the DOM and a second binding would open two tabs per `Ctrl+T`.
- **The address bar has an edge again.** It was drawn with a transparent border held in reserve for the focus state, and the pill's own colour sits close enough to the toolbar's that with nothing round it the most-used control in the browser read as a smudge rather than as a field.
- **An update installs without putting the wizard in front of you again.** You have already been asked, in the browser's own prompt, and pressed Restart now; showing the full NSIS wizard after that is asking the same question twice. It also skips the part that looks broken — pressing Finish leaves that wizard titled "Not Responding" for a few seconds while NSIS deletes the couple of hundred megabytes it extracted to a temp directory. That is the installer's own cleanup on its own UI thread, and nothing here can hurry it; an update that never shows the wizard never reaches it. A first install from a downloaded `.exe` is unchanged, because there the wizard is the point.

## 1.4.0

Downloads and developer tools stop being somewhere else. Both were arrangements that read as a second application bolted to the browser — downloads were a section of Settings, the inspector was a window of its own — and both are now part of it. Along the way, five things 1.3.0 shipped wrong on its first screen, and five more found by a review pass over all of this.

The suite has grown from 89 checks to 105.

- **Developer tools dock inside the window.** They opened in a separate window, which made them read as a second application tied to the browser rather than part of it. They now open beside the page or under it, in a view the browser lays out itself, and **Settings → Advanced** chooses between the two and the old separate window. Changing it moves an inspector that is already open.
- **How that works, since Electron does not offer it here.** Its own docking is implemented by the owning `BrowserWindow`, and this browser has none - it is a `BaseWindow` holding sibling views. So the inspector is hosted the other way round: `setDevToolsWebContents` points it at a view we create and position like any other. Measured working before anything was built on it, which also turned up the thing that would have broken the governor quietly - `isDevToolsOpened()` reports **false** for an inspector hosted this way, so every check for "is this tab being inspected" now goes through the tab rather than through Chromium. Without that the page under an open inspector would have been eligible for discard.
- **Windows Hello reported itself unavailable on machines that have it.** The availability probe asked WinRT a question using `System.WindowsRuntimeSystemExtensions`, which lives in an assembly Windows PowerShell does not load by default — so the type was simply not there, the probe reported "Windows Hello could not be queried", and Settings said the machine had no Hello. The prompt half of the same file loaded that assembly; the probe half did not. Both share one prelude now, and when it does fail it names which PowerShell it was talking to, because there is one cause no amount of loading fixes: PowerShell 7 runs on .NET 5+, which dropped WinRT projection entirely.
- **Downloads, the way Edge does them.** A button appears in the toolbar once there is something to show, with a bar that fills while a file is arriving, and pressing it drops a panel of recent downloads: live progress, **Open file** when one finishes, cancel while it runs, middle-click to reveal it in the file manager. `Ctrl+J` and the menu item open the same panel. It shares its machinery with the app menu rather than having its own — same transparent view, same placement, same dismissal — so the two panels in the toolbar cannot drift apart, and opening one takes the sheet from the other instead of leaving both up.
- **And the full page behind "See all", at `debrowser://downloads`.** Downloads were a handful of rows inside Settings, which is the wrong place for a list that changes while you are looking at it — it is a live thing, not a preference. The page shows each file with the site it came from, how far through it is over how many connections, and one button that cancels while it is running and clears once it is not. It polls only while something is actually moving, so an open downloads page with nothing running costs nothing.
- **Pressing the three dots no longer flashes white.** The menu's view was added to the window before its page had even started loading, and a window-sized view with nothing painted in it is a window-sized white rectangle. The transparency it already had was real and not enough: that governs what the view composites where the *page* is transparent, and until the page exists there is nothing to be transparent. It goes on screen once it has something to show — which also fixes a blur arriving mid-load being treated as the user clicking away, closing the menu in the same breath as opening it.
- **Bookmarks are gone from the three-dot menu.** They have a bar now, which is where people look for them.
- **A new tab opens without waiting for a renderer to start.** It was only instant when one was already open, and the reason turned out to be the process rather than the page: every page the browser serves itself is one site, so they share a renderer, and the second new tab page is fast because the first started it. Resting the pointer on the **+** or the menu now starts that renderer while the pointer is still travelling — measured at 79ms cold against 46ms after a warm-up, and it covers Settings and History too, since they land in the same process. The warmed renderer is held for twelve seconds and then dropped: hovering the + and walking away must not leave 13MB behind, which is the thing this browser exists to argue about. It declines entirely when one of its own pages is already live, or while an animation is being kept smooth.
- **A bookmarks bar, under the toolbar.** Bookmarks were being saved with nowhere to show them: the star worked, the store worked, and the only place the list appeared was Settings. The bar shows each site's own logo and title, opens in this tab on a click and in a new one on middle-click or ctrl-click, and `Ctrl+Shift+B` shows and hides it. With the tab strip down the side it costs the page nothing, because the chrome already owns a full-height column there.
- **Switching tabs hides the inspector rather than destroying it.** Breakpoints, console history and a filtered network log survive going to another tab and coming back, which is most of what anyone does while debugging.
- **Site logos no longer sit on a coloured tile.** The letter chip behind a favicon is a stand-in for a logo, and the code that drew it assumed the icon would cover it once it loaded. Almost no favicon is opaque and square — most are transparent PNG or SVG, and `object-fit: contain` letterboxes the rest — so every site logo in the browser was painted on a hue-coloured square with the site's initial showing through it. The chip now stops painting the moment a real icon loads, in the tab strip, the task manager and the history list. Guarded by a check against the live strip rather than a fixture, because the way this goes wrong is CSS specificity: the theme variants qualify the chip with `body[data-theme=…]`, so a rule that looks right in isolation quietly loses to them.
- **The new tab page is governed like any other tab.** Debrowser's own pages were exempt from every tier below ACTIVE, on the reasoning that they are few and were opened to do something. That is true of Settings and History and false of the one internal page a user can have fifteen of. Fifteen blank tabs sat pinned at ACTIVE, the live-renderer count read 15 against a cap of 12, and the governor was forbidden to touch any of them. The new tab page is now exempt by what it is — a page with nothing to lose — rather than by being internal; typing in its search box makes it dirty like any other page and the existing rule protects it. Settings and History keep their exemption, and the suite now asserts both halves.
- **The task manager shows how many tabs hold a renderer, not a ration.** It read `15/12`, which is accurate and reads as a quota the browser is failing to keep. Tabs are never rationed and the cap is an internal reclaim threshold, so the fraction invited exactly the wrong question.
- **Five fixes from a review pass over all of the above.** A docked inspector stayed painted over the wrong tab, because attaching a tab returned early for a view that was already there — which is true of every tab switch. The new tab page could lose a half-typed query: taking its blanket protection away rested on a dirty-input flag set by a preload the browser's own pages do not carry, so the reasoning was sound and the mechanism was absent; the page reports it directly now. The downloads flyout ignored the chosen theme, because the state broadcast reached every view except the sheet. The prewarmer held the only uncaught `loadURL` in the browser process, and it is closed mid-load by design. And `Ctrl+Shift+B` inverted a value that is hard-`false` with the tab strip down the side, so there it could only ever switch the bar on.
- **Settings no longer claims to be up to date before it has asked.** The first update check is deliberately a minute after launch, to keep a network request and a signature check off the busiest moment the browser has — and for that minute the page asserted a version comparison nobody had made. "Never checked" and "checked, nothing new" are now different states, and there is a **Check now** button for anyone who does not want to wait for the interval. Pressing it works with automatic updates switched off, which stops the browser checking on its own rather than making it refuse to answer; a check that finds something then says so instead of downloading it unasked.

## 1.3.0

The browser's own interface, rebuilt. Nothing in the governor moved: every memory figure quoted for 1.2.0 still stands, and the suite that proves them has grown from 74 checks to 89.

What is new: a history page, Chromium's developer tools, an app menu Debrowser draws for itself instead of asking the operating system for one, real site logos wherever a page is listed, and the whole interface set in Aptos and Calibri on a design system that finally lives in one file. Six defects found by a review pass over all of it are fixed here too, two of them worse than they were reported.

- **The three-dot menu is drawn by Debrowser instead of by the operating system.** It used to be `Menu.popup()`, for a reason that was true — the chrome is a view clipped to its 84px strip, so a dropdown drawn there stops at the toolbar's bottom edge, and a menu that cannot overflow its own window is not a menu. The way out is a second view, window-sized and transparent, created when the menu opens and destroyed when it closes: the menu can be drawn anywhere in the window, and the empty part of the view catches the click that dismisses it, which is the job a system popup does with a pointer grab we cannot take. Verified rather than assumed — a transparent `WebContentsView` really does composite over the views beneath it, measured by reading the X framebuffer with the menu open.
- **What that buys:** the menu matches the browser rather than matching Win32, it themes and animates with everything else, and it can hold a control a platform menu item cannot. Zoom is now a stepper showing the current percentage, where it was three items behind a chevron — 100% to 125% and back used to be four interactions.
- **What it costs is paid rather than assumed.** A system menu brings keyboard navigation and a screen-reader identity for free; this one implements them: arrows, Home/End, Enter, Escape, a Tab loop that cannot walk out of the sheet, and a real `role="menu"` of real buttons. The menu's contents are data now, sent from the browser process, and each item's `id` *is* the command it sends back — so there is one list of what the menu does rather than two that drift. The suite checks that every item names a command the bridge will actually carry, and that the menu's renderer is destroyed when it closes.
- **A history page, at `debrowser://history` or `Ctrl+H`.** Search by title or address, open in this tab or a new one, forget a single page, or clear the lot. Entries are grouped by day under sticky headings, and each carries the site's initial on a colour derived from its hostname.
- **History keeps one row per page, not one per visit** — with a visit count and the last time — so the store stays proportional to the number of distinct pages seen rather than to how often they were seen, which is the difference between bounded and unbounded in exactly the workload this browser is for. Capped at ten thousand pages, written a few seconds after a change rather than on every navigation, and flushed on quit.
- **It is plain JSON in your profile directory, and that is deliberate.** Encrypting the list of pages you visited would hide it from you and from nobody else, since anything that can read the file can reach the key. The browser's own pages are never recorded, `javascript:` and `data:` addresses are refused, and the switch that stops recording sits beside the list it governs. Turning it off leaves what is stored alone: not adding to a record and deleting one are different decisions, and the page has a button for the second.
- **Developer tools: Chromium's own, the whole suite.** Elements, Console, Network, Performance and Sources are already in the engine this browser is built on, and a hand-made inspector beside them would be worse at every one of those jobs. Opened detached, from the menu or `F12`, so it is a window you can move to another monitor and costs nothing while it is closed.
- **A tab under the inspector is held at `WARM`** — never frozen, never discarded. Freezing a page stops the task queues the inspector is driving, so a frozen tab under DevTools is an inspector attached to something that will not answer; and a tab discarded out from under a console session is a browser that looks broken. It rejoins the ladder the moment the tools close, which is asked of the renderer rather than tracked here, because the tools can be closed from their own window and nothing tells us when.
- **Browser shortcuts work while a page has the keyboard.** Every one of them was bound in the chrome renderer, which is a different renderer from the page — so they stopped working the moment you clicked into a page, which is most of the time. Chromium does not bind them itself either: they are the browser's, and this browser has no application menu for Electron to take them from. They are intercepted before the page sees them now, and only the ones in the table are taken.
- **Both tab bars have a colour.** The chrome was four values of the same neutral and read as a wireframe of a browser rather than as one. A few percent of the accent is mixed into each surface and more of it into the states that mean something: the strip fades from an accent tint, the active tab is a lifted surface with a 2px accent bar along the edge it meets the strip on — down the leading edge in the vertical layout, the way Arc and Zen mark a row — and every hover is a wash of the accent rather than another grey. It follows whatever accent you have picked, so there is nothing new to theme.
- **A tab without a favicon shows the site's initial on a colour derived from its hostname.** This is most of what stopped the strip reading as one long grey bar: a favicon takes a round trip and is often never sent, so a row of tabs opened at once was a row of identical grey placeholders, permanently for any site without an icon. The history list uses the same colours from the same function, so a site looks the same in both.
- **The interface is set in Aptos, then Calibri, then whatever the system has** — both are Microsoft's and neither can be bundled, so the stack degrades and names Carlito, the metric-compatible open font, before the system default. Two things were measured before anything was restyled around them, rather than taken on trust. Calibri's x-height is 0.48em against 0.50–0.55 for the faces desktop UI usually assumes, so at an unchanged 13px it read small: the base size is 14px now, which lands on the same apparent size in about 10% less width. And `font-weight` 300, 400 and 500 all rasterise identically in Calibri, as do 600 and 700 — the face ships Regular and Bold and nothing between, so every `550` and `600` in this UI was quietly asking for full bold.
- **So emphasis is carried by colour and size, not by weight.** Settings rows, menu items, the active tab and the history list all used a semibold that does not exist in this face and would have come out shouting. Bold is now spent only where something genuinely leads — a page title, a live figure — which is a better hierarchy than the one it replaces and would have been the right call in any typeface.
- **theme.css is the design system now**, not just the palette: type scale, weights, tracking, a 4px spacing scale, radii, one elevation token, one focus ring, and the accent tints the whole UI is built from. Each was previously a number written in place, several times, slightly differently. The focus ring in particular is declared once on `:focus-visible`, so a new control is correct before anyone remembers to style it.
- **Details that were the platform's and are now ours:** thin themed scrollbars, selection in the accent, a placeholder that reads as a prompt rather than as content, and dividers inside a card set lighter than the card's own edge so a group of settings stops reading as a table of them.
- **The settings page says less.** Every setting carried a two- or three-sentence justification, which is documentation wearing a settings page's clothes; each is one line now. The reasoning was not deleted, it was already in the code comments and the README, which is where it belongs.
- **Elevation in Settings goes the usual way round.** The page was the raised surface with the rows cut into it as darker wells, which put the darkest thing on screen around the text you are reading; the page is now the base and the cards sit above it, matching the task manager, which was already doing it that way.
- **The sidebar's toolbar was in the wrong order, and the reason is worth knowing.** An unset `order` on a flex child is 0, which sorts *before* 1 — so the bookmark star, the one control with no explicit order, was not left where it was but moved to the front of the row, ahead of the back button. Every control in that row is ordered explicitly now, and the memory meter takes the column's full width instead of wrapping: across the top it is a 46px sliver, and down the side it is a bar the width of the sidebar.
- **The active tab is the same colour as the toolbar**, which is the shape every browser draws and the reason a tab has rounded top corners and square bottom ones — the tab and the toolbar are one surface, and the strip is what they sit in front of. It had a gradient of its own, which made it read as a button parked above a bar.
- **Tabs show the site's own logo.** They always could — the browser has always been told where a page's icon is — but an icon that failed to load was left as a broken image rather than falling back, and the fallback letter was hidden the moment an address arrived. Measured, that is not an edge case: Chromium reports an icon address for *every* page, defaulting to `<origin>/favicon.ico` when the page declares nothing, and plenty of sites do not serve it. The letter now sits behind the image and comes back if the image never arrives, so a tab shows a logo, or a letter, and never a broken picture. The content policy was also refusing `http:` icons outright, so no icon from an unencrypted site could ever have loaded.
- **The task manager and the history list show them too**, from the same `siteHue` the tab strip uses, so a site is one colour everywhere. History stores no images and no addresses it can work out for itself: the default `/favicon.ico` is derived from the row's own URL, and only a site that puts its icon somewhere else costs a stored string.
- **A loading tab spins where its icon is**, as in Chrome. The line under the toolbar says *something* is loading; with twenty tabs open and three of them working, it does not say which.
- **The padlock is drawn rather than typed.** It was the 🔒 emoji, rendered by whichever colour-emoji font the machine happens to have, at whatever size that font decided — on the one element in a browser that should never look like it came from a chat message. It is a stroked glyph now, and an unencrypted page gets its own mark in the warning colour rather than simply nothing, which is the state that ought to be visible.
- **The menu is grouped the way Chrome groups it**, because that ordering is twenty years of muscle memory and there was nothing to gain by being different: what you opened, where you have been, what this page can do, what the browser can do. What is *in* each group is still ours.
- **Downloads, Bookmarks and Full screen are in it now.** The first two were only reachable by opening Settings and scrolling, which is not a place anyone looks for their downloads; they are deep links, so `Ctrl+J` lands on the downloads section rather than at the top of a settings page, with the section marked for a moment so the jump is explained rather than merely made. Full screen is `F11`, and it did not exist at all.
- **Zoom's Reset moved to the end of its row**, after the stepper it resets. In the middle it read as a word wedged between a label and a control, and you had to work out which of the three it belonged to. The row's label is also indented to the icon column now, so it starts where every other label in the menu starts.
- **Fixed: the security indicator could be set but never cleared.** `hidden` is a property of `HTMLElement`, and the padlock is an `<svg>` — measured, `'hidden' in svg` is false, so assigning it defined a stray property and never touched the attribute, and Chromium's `[hidden] { display: none }` rule does not apply to SVG either, so the attribute in the markup did nothing. The two cancelled out into a real fault: a padlock drawn on a website stayed on screen after moving to `debrowser://settings` — an encrypted-connection claim on a page that has no connection. It is driven by an attribute the stylesheet can see now, and the paths are cleared as well as the element hidden, because this is the one element where being wrong in the reassuring direction is worse than not being there.
- **Fixed: a new page inherited the last one's name and icon.** `did-navigate` updated the address and nothing else, and the history entry is written from that event — so a row was recorded under the title of the page you came from, and the previous site's custom icon address was persisted as though it belonged to the new one. Both are cleared at commit now, which is also when a browser stops showing you the old page's title.
- **Fixed: a failed download left a full-size file behind.** The file is allocated to its whole length before the first byte arrives, so a download that died part way through left something of exactly the right size with zeros in the gaps — an installer that looks complete in a file manager and is not. Cancelling already deleted the file for this reason; failing did not, which is the path you did not choose and are less likely to be watching for.
- **Fixed: dismissing the menu made the button dead for a quarter second.** The guard that stops the three-dot button from reopening a menu its own click just closed was armed by *every* close, so Escape — or clicking an item — then reaching for the button again did nothing. Only the focus-loss close arms it now, which is the only one that races.
- **Fixed: the history page was fetching icons as the page itself**, with this session's cookies, from every site on screen. That is the request Chrome avoids with a local favicon store, and it announces that you are reading your history. See the note in the README: the browser process fetches them now, credentials omitted, and the pages' content policies permit no other image source.
- **Fixed: the menu view stamped its close time twice**, and `history.all().length` copied the whole ten-thousand-entry store to read a number that was already to hand.
- **Fixed: the tab strip was painted dark in the light theme.** `var()` inside a custom property is substituted where the property is *declared*, not where it is used, and the strip's colour was declared on `:root` while both palette overrides live on `<body>` — so it resolved against the dark palette and inherited that down whatever theme was in force. It had been wrong on every view that draws a strip.

## 1.2.1

The Intune package, in the format Intune actually deploys. Windows only, and nothing else in the browser changes.

- **1.2.0 shipped the Intune variant as a bare `.exe`, which cannot be deployed to Intune at all.** A Win32 app is a `.intunewin`: a bundle holding the installer encrypted with AES alongside a `Detection.xml` that the service reads when you upload it and the Intune Management Extension decrypts on the device. An `.exe` has none of that, so the portal rejects it at the upload step — the packaging was correct in every respect except the one that makes it usable.
- **It is now built in CI, by Microsoft's own tool.** The Win32 Content Prep Tool is the only thing that produces the format; the encryption and the metadata are an undocumented contract with the service, and a reimplementation would produce a file that uploads cleanly and then fails on a device, which is the worst place to find out. The tool is pinned to an immutable commit and its SHA-256 is verified before it runs, because it executes in CI with the repository checked out.
- **Both halves ship.** The `.intunewin` is the only deployable artifact, and the `.exe` is the only one you can install by hand to test, because the copy inside the bundle is encrypted. The release refuses to publish with either one missing.
- **Published as a pre-release, deliberately.** It is still untested against a real tenant, and a pre-release is not GitHub's "latest", so it cannot be mistaken for the build an ordinary user should download. It carries no `latest.yml`, so the in-app updater never offers it either.
- **It stays off the normal release path**, on its own workflow, published on demand. A release aimed at people installing Debrowser themselves has no reason to carry an artifact none of them can run — and building a bundle means fetching and hash-checking Microsoft's tool, so on the shared path an upstream file moving would have failed every platform's release over something none of them contain.

Nothing in the browser itself changed between 1.2.0 and 1.2.1. If you are not deploying through Intune, 1.2.0 is the release you want.

## 1.2.0

Updates that download only what changed, the browser's own pages, saved sign-ins, honest memory figures off Linux, and a great deal more personalisation.

| | Before | Now |
|---|---|---|
| **Updating** | Re-download the whole ~110MB installer by hand | Only the blocks that changed, then it offers to restart |
| **Memory on Windows and macOS** | Summed working set — measured at 1.95x reality, labelled "over-counts" | Measured natively per process, and the measure is named |
| **Settings** | An overlay that trapped the browser on it | A real page at `debrowser://settings`, with a URL and a tab |
| **New tab** | example.com | `debrowser://newtab` — ours, empty, no network requests |
| **Passwords** | Nothing could be saved | Saved on request, encrypted by the OS keystore |
| **Personalisation** | Accent colour | Tab strip colour, translucency, window material, motion, hardware acceleration |

### Updates

- **Differential downloads.** electron-builder writes a blockmap beside each installer describing its compressed stream in content-defined chunks, so an update fetches only the blocks that differ and reuses the rest from the installed copy. Almost all of a 110MB artifact is Chromium, which does not change between our releases.
- **The plumbing existed and was inert.** Blockmaps and `latest*.yml` manifests were already being generated into `dist/` on every build, but the workflow's per-platform artifact globs listed only the installers, so none of it ever reached a release. An installed copy had nothing to read even if it had known where to look — and it did not, because no `publish:` provider was configured, which is what writes `app-update.yml` into the package.
- **Nothing installs behind your back.** The updater checks a minute after launch rather than during it, downloads in the background, and then asks. It never installs at quit: this installer is assisted rather than one-click, so it puts its own window on screen, and doing that unannounced during a restart nobody chose would lose the session to a surprise.
- **macOS is honestly absent rather than quietly broken.** Squirrel.Mac validates that an update is signed by the same identity as the running app and refuses outright when there is none, so an unsigned build cannot self-update at all. The capability reports that by name, as does the settings page, in the same `{available, reason}` shape the hibernation backend uses — an inert feature that cannot say why is indistinguishable from a broken one. The same applies to `.deb`, `.tar.gz` and the Windows portable build, which are not updatable formats.
- **A switch in Settings.** Off means the browser never reaches the network to look for a version, which is a privacy choice as much as a bandwidth one. It is read live, so turning it off takes effect at the next check rather than the next launch.

### The browser's own pages

- **Settings no longer traps the browser on it.** Opening Settings covered every tab with a view that nothing dismissed, so switching tabs appeared to do nothing and the browser looked frozen on a page with no way out. It was not frozen: it was drawing the page behind a lid with no handle. The fix is not a dismiss call in more places — it is that the browser's own pages are now *pages*, served under a real `debrowser://` scheme, with URLs, titles, tab strip entries, history, and back and forward that work. There is no lid because there is no overlay. Covered by a check that would fail against the old design.
- **A new tab page of our own**, at `debrowser://newtab`, instead of example.com. Deliberately close to empty: it is the most-opened page in the browser, and a start page of tiles and feeds would also be the most expensive one. No network requests at all — no fonts, no favicons, no suggestions — and it shows what the browser is actually for, the current total and the per-tab figure.
- **The browser's own pages are exempt from the governor.** Every tier below ACTIVE is wrong for them: freezing one stops the page servicing the controls being operated, and discarding one throws away a half-filled form and reloads as though the browser had crashed.
- **A privileged page can never become a privileged web page.** Internal pages carry the command bridge in their preload, so a link in Settings that navigated the same renderer to a site would hand that site's JavaScript the run of the browser. Navigation away from `debrowser://` is cancelled and handed to an ordinary tab, which is also what a user wants from a link in Settings. The protocol handler resolves every path and refuses anything outside the directory it serves.
- **Animations wait until the page is on screen.** A view that is not composited has its animation frames throttled hard, so an entrance animation started while a tab is realised in the background is still part-way through when the tab is finally shown — the page arrives half-faded and settles afterwards, which reads as a rendering fault. This browser realises tabs in the background routinely, so that was the common case rather than the odd one. Found by looking at a screenshot rather than by reasoning about it.

### Appearance and settings

- **Personalisation beyond the accent colour.** The tab strip gets its own colour, deliberately separate: it is the largest painted area in the window, and what works as a 3px focus ring rarely works across the top of a screen. A "match the accent" option is there for anyone who would rather not choose twice. Window translucency is a slider, and on Windows 11 the system can paint its own blurred material behind the window.
- **Translucency costs essentially nothing**, which is why it is done this way. Real per-element transparency means a window with an alpha channel and a blur pass on every frame; this asks the OS compositor, which is already drawing this window and every other one on the screen, to draw it slightly differently.
- **Hardware acceleration can be turned off.** A real diagnostic setting rather than a knob: bad GPU drivers show up as flicker, blank views, or a browser that will not start, and this is the first thing to try. Chromium decides at launch, so the preferences file is now read before the app starts rather than after, and the setting says a restart is needed rather than pretending to apply.
- **Small animations, and a way to stop them.** Tabs arrive, buttons press, rows and swatches respond. Everything that moves is a transform or an opacity change on a small element, so it stays on the compositor and never causes layout — the chrome is a live renderer for the whole life of the window, and an animation that reflowed it would undo part of what the governor saves. The system's reduced-motion setting is always honoured, and there is a switch for machines not set that way.
- **The task manager stopped explaining itself.** It is a live instrument — what each tab is holding, right now, and why — and a paragraph of prose beside a number that changes twice a second is noise in front of the thing you opened it to read. The explanations moved into Settings behind "Explain the memory figures", off by default. The "over-counts" label stays visible either way, because a wrong number with no warning is the one thing that is not acceptable.
- **Mojeek replaces Brave** in the search engine list. Both crawl their own index rather than reselling Google's or Bing's results, so the list keeps an independent option; Mojeek's index is smaller, which shows on obscure queries.

### Memory, measured honestly everywhere

- **Memory is measured natively on Windows and macOS instead of being summed and apologised for.** Summing each process's working set counts a shared page once per process that maps it, and the largest shared thing in a Chromium browser is Chromium itself, mapped into every renderer — measured at 1.95x the proportional figure across five processes and rising with process count, so two open tabs could read as 1098 MB. A small helper now ships beside the app: on Windows it walks each process's working set and divides every shared page by its share count, which is proportional set size computed the only way Windows offers; on macOS it reads `phys_footprint`, the figure the OS charges each process and Activity Monitor shows. Linux is untouched and does not build it — `smaps_rollup` already reports Pss, and a second path to the same number would be one more thing to keep honest.
- **Both new figures are approximations, and say which kind.** Windows caps a page's share count at seven, so a page shared by more processes is counted slightly high — and a Chromium browser runs close to seven processes, so that is not hypothetical. macOS's footprint excludes the clean file-backed pages that caused the over-count but does not divide shared dirty pages, so it is not proportional set size. The panel names the mechanism on hover rather than presenting either as exact.
- **The child-process machinery is now written once.** The trim helper's spawn, line protocol, timeout, restart and EPIPE handling were the subtlest code in the project and every unusual line in them exists because something broke. A second helper meant either a second copy to keep correct or extracting the first; it is extracted, and the trim path was re-verified against the real binary afterwards.
- **Two bugs the tests caught, both of which would have shipped.** `protocol.handle` registers on the default session only, and tabs run in their own partition — so the browser's own pages failed to load inside a tab while rendering perfectly in a default-session harness. And once a page loads, the tab reports the URL Chromium normalised it to, with a trailing slash, so matching "is settings already open?" by URL string stopped matching the instant the page finished loading and every subsequent open would have made another tab.

### Saved sign-ins

- **Saved sign-ins and payment details, encrypted by the operating system.** The browser asks after you sign in and stores nothing unless you say yes — a dialog drawn by the browser, not by the page, because the one question that must never be imitable is "shall I keep your password". Records are AES-256-GCM under a 32-byte key held by DPAPI, Keychain or libsecret; the key never exists in plaintext on disk, and whole records are encrypted rather than just the secret, so the file does not publish which services you have accounts with.
- **No weaker fallback, ever.** Where no real keystore exists the store refuses to save and says so. On Linux, Electron reports encryption as "available" while quietly using a basic-text backend that only obfuscates; that case is detected by name and refused, because saving credentials under it while telling you the OS protects them would be a lie the UI told on the browser's behalf.
- **The existing refusals are untouched.** Password and payment fields are still never read into the session store, and a page carrying one is still never photographed. That is not a contradiction: the session store is a performance mechanism you never opted into, so putting a password in it would be a decision made for you. This is the opposite — a deliberate answer to a question.
- **Passwords fill, payment details do not.** A password fills on load only when exactly one saved sign-in matches the page's origin, matched per origin rather than per domain, so a sibling subdomain gets nothing. Card numbers are filled only on a click, because a page can place a hidden or off-screen payment field and a card number is not bound to any site the way a password is.
- **Fills dispatch real input events.** Setting `value` directly leaves a field looking empty to React, Vue and Angular, which track state outside the DOM — the form would submit blank while appearing filled, which is worse than not filling it.
- **One definition of "sensitive field", where there were two that disagreed.** The screenshot gate matched the `autocomplete` attribute with an exact selector; the session snapshot matched the IDL property with `===`. Neither handled a token list, so `autocomplete="cc-number webauthn"` — which is valid — matched nothing, and such a field would have been read into the session store and its page photographed. Now tokenised, and covering CVC and expiry as well as the number.
- **The manager never receives secrets.** A row needs a site and a username; revealing one is a separate call for a single record. It is also fetched on request rather than riding the state broadcast, which reaches three views on every governor tick.

### Found in review, before any of it shipped

- **A website could have read every saved password.** The omnibox navigates with `loadURL`, which does not fire `will-navigate`, so the confinement on internal pages did not apply to it — and because every tab now opens on `debrowser://newtab`, every tab was built with the privileged preload and marked as one of the browser's own pages for the rest of its life. A site loaded into one inherited the bridge and passed the check guarding the credential store. Privilege is now decided from the sender's **live URL** rather than from a flag or from whichever preload a renderer happens to carry, because neither of those can be revoked once a renderer exists. Found in review before release; no build carrying it was ever published.
- **Every tab was also exempt from the governor**, for the same reason: `internal` was computed once from the URL a tab was created with, and every tab is created on the new tab page. Nothing would ever have been frozen or discarded. The flag now follows the current URL.
- **Settings and the new tab page were sent no state at all.** Both build their entire UI from the state message, and when the settings overlay became a tab, `publish` was not updated to reach tabs — so Settings would have rendered as a column of empty headings. Every existing check still passed, because they asserted on the tab rather than on the page.
- **Commands from those pages were being dropped**, so no preference could be set and the new tab search box did nothing; payment fill targeted the Settings tab the user had just clicked in and always refused; and the saved-password fill was hung off a `once` handler that only ever fires for a renderer's first document, which is the new tab page — never a sign-in page.
- **Smaller ones from the same pass:** a credential prompt with no in-flight guard, which a page submitting a form in a loop could have stacked into a lockout; a truncation boundary that made a maximum-length password fail to save after the user agreed to save it; `remove()` throwing instead of refusing on an unknown kind; the Brave→Mojeek change silently resetting anyone who had chosen Brave; and internal pages 404ing for anyone whose install path contains a `#` or a `%`.
- **The tests could not have caught any of this**, which is the more important finding. Under `--smoke-test` the home page is a local fixture rather than `debrowser://newtab`, so the suite never exercised the path every real tab takes. It does now: a tab is opened on the new tab page, navigated to a site, and checked to have stopped being privileged, to have become governable again, and to be refused when it tries to use the bridge it inherited.
- **Every link on every website would have opened a new tab.** The confinement that keeps the browser's own pages from navigating to the web is installed once, when a renderer is built — and every renderer is built on the new tab page, so it went on cancelling navigations for the tab's whole life. Clicking any link, or submitting any GET form, was hijacked. It survived the tests because they navigate with `loadURL`, which does not fire `will-navigate` at all; the new check drives a real link click.
- **A boost could stand the governor down permanently.** A boost was only ever released when the boosted tab was also the active tab, so switching away from an animating page left it boosted forever — and with it `quiesceRequested`, which pauses budget enforcement, the live-tab cap, heap limits, hibernation and speculation. Nothing would have been reclaimed for the rest of the session, and closing the tab made it unrecoverable. The whole memory story would have been quietly off.
- **A closing tab could impersonate the browser UI.** "No tab matches this sender, so it must be the chrome" is not safe: a tab is removed from the list before its renderer is torn down, and in that window a website could land a command — `set-pref` on the homepage persists, which is a durable hijack. The chrome views are identified by name now. Credentials were never reachable this way; that channel demands Settings specifically.
- **Typing a `debrowser://` address into the omnibox produced a dead page**, because the preload is fixed when a renderer is built and a tab realised on a website has the page probe rather than the command bridge. Internal addresses now go through the page opener, which focuses the existing Settings tab or makes a new one.
- **Also:** `--no-governor` crashed the IPC handler on a manual discard or a budget change, and the error page interpolated the failing URL into an inline script with `JSON.stringify`, which does not escape `</script>` — the comment beside it claimed injection was impossible.

### Deploying with Intune — experimental

- **An Intune-shaped Windows installer**, `Debrowser-1.2.0-win-x64-intune.exe`, alongside the normal one. It differs in exactly two ways, both forced by how the Intune Management Extension works: it installs **per machine** rather than per user, and it is **silent**. The IME runs install commands as SYSTEM, so a per-user installer lands in SYSTEM's own profile where no real user will ever find it, and an installer that waits for someone to click Next never finishes because nobody is there.
- **This has never been run against a real tenant.** It was written on Linux, in a container with no Windows, no Intune and no way to test any of it — the install commands and detection rules are derived from documented IME behaviour, not from a deployment anyone watched succeed. `build/intune/README.md` carries the full disclaimer, the `.intunewin` packaging step, the detection rule, and the failures worth checking first. Pilot it on a test device.
- **Unsigned is likely to be the real blocker**, not the packaging. WDAC, Smart App Control and AppLocker refuse an unsigned binary installed by SYSTEM, and no packaging works around that.
- **The browser notices it is managed.** A machine-wide install cannot write to its own directory as an ordinary user, so the built-in updater turns itself off and says so in Settings rather than failing a download every six hours against a permission the user cannot grant. In a managed estate the update schedule belongs to whoever runs the estate. Settings, session and saved credentials stay per user, so they survive upgrades and one user cannot read another's.

Verification: 59 checks, all green, including these — that the updater is inert outside a packaged build and names the reason. Packing was checked rather than assumed: this project's `files:` allow-list does not mention `node_modules`, so the new dependency could plausibly have been left out of the archive and crashed only on an installed copy. It is packed, and `app-update.yml` lands beside it.

## 1.0.1

Two Windows reporting-and-rendering bugs, both reported from a real install.

- **Minimising the window brought it back empty.** No tab strip, no page, just the background colour and the native menu bar. Minimising on Windows fires `resize` with a client area of zero, and the layout computed from it, flattening every view to zero width — with nothing to restore them afterwards. `layout()` now refuses to compute from a minimised or zero-sized window, and `restore`/`show` re-run it and re-assert view visibility. Confirmed against the old code, which flattened the chrome from 1280px to 0; the new code holds it. Covered by a smoke check, since the failure cannot be reproduced under xvfb where there is no window manager and `minimize()` is a no-op.
- **The memory figure over-counts off Linux, and did not say so.** Windows and macOS have no cheap proportional measure, so the total is summed working set, which counts each page shared between processes — chiefly one copy of Chromium in each — once per process. Measured at **1.95x** the proportional figure across five processes, rising with process count: two open tabs could read as 1098 MB. The panel now labels it "resident (over-counts)" there, explains it on hover, and notes that the budget is compared against the same inflated total so the governor reclaims earlier than it needs to. No better number is available — Electron's `ProcessMemoryInfo` declares `private` and `shared`, but `getAppMetrics()` populates only `workingSetSize`.

## 1.0.0 — first stable release

A complete browser whose governor decides, every two seconds, how much memory and CPU each tab is allowed to hold. Everything below was measured on real renderers and real pages; levers that failed measurement were deleted rather than shipped quiet, and the ones that were deleted are recorded in `docs/MEASUREMENTS.md` on `claude/research-build`.

### The headline

**45 tabs in 365 MB — 8.1 MB per open tab**, against 822 MB (18.3 MB/tab) for the same workload with the governor off.

The cost model, fitted across every benchmark run and stable since:

```
total(n) = 238 MB fixed + 0.6 MB × tabs_open + 13.2 MB × min(tabs, live cap)
```

Read every per-tab figure with its tab count. The fixed 238 MB is Electron's, amortised across whatever is open, so per-tab memory *improves* as you open more — and below about 25 tabs nothing can reach 10 MB/tab, because the fixed cost alone exceeds it. The 13.2 MB is Chromium's per-renderer floor and does not move; the win is residency, not smaller renderers.

### What it does

- **Six tiers.** `ACTIVE → WARM → COLD → FROZEN → HIBERNATED → DISCARDED`, driven by idle time and memory pressure.
- **Invisible discard.** A tab past the live-renderer cap is discarded but stays open, keeping history, scroll and typed input, and returns behind a thumbnail of how you left it. p95 to placeholder is well inside the 50 ms budget; restore p50 is ~5 ms.
- **Hibernation** (Linux, with zram or swap and `CAP_SYS_NICE`). Freeze, then hand the renderer's cold pages to the OS compressor. Nothing is lost and there is no reload. On a 12-tab heavy-heap workload: **1409 MB → 481 MB**, seven tabs hibernated, nothing discarded, `MemAvailable` up 435 MB.
- **Animation-aware boosting.** A page that animates gets the CPU to hold its frame rate and gives it back when it stops; everything expensive in the browser stands down while it does.
- **Protections that always win.** The visible tab, audio, typed input, a tab you just left, and a tab already at its floor.

### Measured, and kept honest

- **Proportional (PSS) accounting, not summed RSS.** Summing RSS counts one copy of Chromium per renderer and overstated this project's own figures by 3x before it was corrected.
- **Zygotes counted.** `getAppMetrics()` omits Chromium's two Linux zygotes (~29 MB of fixed overhead); they are added back.
- **A system-wide figure beside every per-process one.** Pages leaving a process reappear as the compressor's own allocation at about 2:1, so a per-process reading alone overstates a trim by roughly double. The bench prints both and the ratio.
- **Capabilities report why, not just no.** "Not built", "not executable", "needs `CAP_SYS_NICE`" and "no swap to compress into" are four distinct messages, because a user who cannot tell which one they have cannot fix it.

### Known limits

- Restore replays navigation, scroll and unsubmitted input — not in-page JavaScript state. That is why typed input is protected from discard rather than restored from it.
- Password and payment fields are never read into the session store, and a page carrying one is never photographed for a thumbnail.
- Per-tab CPU is exact only when a tab owns its renderer; with one-renderer-per-site, a busy Web Worker in a shared renderer is not a freeze trigger.
- `minimal` profile disables site isolation. That is a security setting. It warns on every launch.
- No extensions, bookmarks, history UI or downloads UI.
- Windows and macOS hibernation backends are deliberately **not** implemented rather than written untested. `trimCapability()` reports `available: false` with the reason.

### Installers

- **Installers for all three platforms.** Windows gets an NSIS installer and a portable single-file `.exe`; macOS gets `.dmg` and `.zip` for both Intel and Apple silicon; Linux gets AppImage, `.deb` and `.tar.gz`. Configured in `electron-builder.yml`, built per-platform on native runners by `.github/workflows/release.yml`, which runs the 41-check suite on each platform *before* packaging it.
- **The trim helper could never have worked in a packaged build.** It was resolved relative to `__dirname`, which lands inside `app.asar` — and a binary inside an asar archive cannot be executed, because the archive is one file the runtime reads rather than a directory the kernel can exec from. Every installed copy would have reported "mem-trim not built" forever, quoting a build command that does not apply to an installed app. It now ships beside the app and is found there.
- **That "not built" message is now audience-aware**, since telling someone with an installed build to run an npm script in a source tree they do not have is the same class of wrong answer as the `setcap` misdiagnosis this release also fixes.
- **Packaged builds can verify themselves.** `--smoke-test` works from an install, because 12KB of fixture HTML ships in the asar. The project is tested on Linux and only expected to work elsewhere, so the means to check travels with it. The first packaged build failed seven checks by serving 404s with the fixtures excluded — including one that looked like a privacy regression and was not.
- The Linux-only trim helper no longer ships inside the Windows installer.

Nothing is signed, but the build is now wired for it: set `CSC_LINK` and `CSC_KEY_PASSWORD` (or the Azure Trusted Signing secrets) and the release workflow signs, with no code or config change — an empty value means "no certificate", so a fork with no secrets still builds unsigned. Signatures are RFC3161-timestamped and SHA-256 only, and the workflow prints the signature status of every `.exe` before uploading, so a release that is quietly unsigned because a secret expired does not get past CI.

`docs/PACKAGING.md` covers getting a certificate, and is worth reading before buying one: since 2023 no CA will sell a downloadable `.pfx`, and an OV certificate does not stop the SmartScreen warning by itself — only EV or Azure Trusted Signing clear it from the first release. It also records what cross-building can and cannot do (the Windows installer needs Wine *including* 32-bit; the macOS `.dmg` cannot be built off macOS; and electron-builder cannot sign a Windows binary from Linux at all, because its vendored `osslsigncode` links against an OpenSSL no current distro ships).

### Verification

`npm run smoke` — 41 checks against real renderers and measured memory, all green. `npm run bench` for the memory comparison. A packaged build can run the same suite against itself with `--smoke-test`.
